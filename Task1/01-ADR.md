## 1. Контекст

«GoFuture» — это платформа для агрегирования такси, у которой есть пассажирское и водительское приложения, а также веб-портал для корпоративных клиентов.
Компания столкнулась с критическими ограничениями монолитной архитектуры.

Монолитная архитектура «GoFuture» тормозит развитие бизнеса, поэтому компании нужно осуществить переход к микросервисам.
---

## 2. Требования

### Функциональные

**FURPS+**:

| Категория | Требование |
|-|-|
| **ФТ-1** | Оптимизация загрузки водителей в часы пик с помощью «умного» перераспределения (ожидание подходящего водителя вместо выбора ближайшего, чтобы избежать «горячих зон», где концентрируется большинство водителей) |
| **ФТ-2** | Соответствие локальным регуляторным требованиям. |
| **ФТ-3** | Поддержка динамического ценообразования в режиме реального времени. |
| **ФТ-4** | Интеграция с локальными платёжными и картографическими сервисами. |

| Категория | Требование | Критичность |

| **НФТ-2** | Автоматическое горизонтальное масштабирование более чем в трёх географических регионах. | Высокая |

## 3. Решение

### Разбиение на домены, создание карты сервисов ###

| Домен | Команда | Задача | Данные |
|---|---|---|---|
| **Booking** | Команда Booking | Оформление заказа, поиск водителя, контроль выполнения поездки | Заказы, данные о поездке |
| **Driver** | Команда Driver | Личный каб. водителя, взаимодействие с водителем, поиск свободного водителя, приём заказов водителем | Данные о водителях |
| **Pricing** | Команда Pricing | Вычисление стоимости маршрута | Данные о маршруте, тарифы |
| **Payments** | Команда Payments | Приём оплаты от пассажиров | Данные об оплатах, банковских картах и платёжных системах |
| **Payouts** | Команда Payments | Выплаты водителям | Данные о выплатах, банковских картах, платёжных реквизитов и платёжных системах |
| **Geography** | Команда Geography | Предоставление карт для навигации, навигация и прокладка маршрутов | Геоданные и статистика загрузки дорог |
| **Analytics** | Команда Analytics | Вычисление статистики | Статистика загрузки дорог, активности потребителей |
| **Fraud** | Команда Fraud | Поиск нарушений | Все финансовые данные |
| **Notification** | Команда Notification | Отпрака нотификаций | Адреса для нотификаций, данные систем отправки нотификаций |

### Порядок действий при разбиении системы на сервисы ###

В качестве главной стратегии разбиения монолита предлагается использовать проверенный паттерн **Strangler Fig**.

Для этого:

1. Перед имеющимся монолитом ставиться фасад-прослойка в виде сервера Gateway API (Kong, Nginx).
2. Добавляется сервер нотификации.
3. Домены один за другим выносятся в микросервисы.

### Очерёдность выноса доменов из микросервисов  ###

Предполагается вынос доменов в микросервисы осуществлять по принципу: от простого с сложному. То есть, в первую очередь выносятся достаточно простые сервисы. Данный способ позволяет:

1. Минимизировать риски ошибок и их последствия.
2. Постепенно снимать нагрузку с монолита и отслеживать повышение производительности как вынесенных сервисов, так и ядра системы, ещё работающего в монолите.

Предлагается следующая очерёдность выноса доменов в микросервисы:

1. **Notification**. *Обоснование:* данный домен не зависит от других и изначально ассинхронен.
2. **Geography**. *Обоснование:* данный домен не зависит от других, содержит специфическую логику и данные, над ним работает команда, которая мало пересекается по задачам с другими командами и легко может быть отделена от общего процесса.
3. **Pricing**. *Обоснование:* После выноса Geography самое время вынести Pricing, который будет обращаться уже к новому микросервису Geography. Вынос Pricing в отдельный сервис позволит не только снизить нагрузку, но выпускать кастомизированные для различных регионов версии данного сервиса.
4. **Driver**. *Обоснование:* После выноса Geography удобно вынести и Driver.
5. **Payments**. *Обоснование:* Выносим домен приёма платежей.
6. **Payouts**. *Обоснование:* следом за доменом водителей, выносим и домен выплат водителям.
7. **Fraud**. *Обоснование:* после того, как все финансовые домены вынесены в микросевисы, новая логика Fraud сможет перехватывать все необходимые для работы данные из появихшихся топиков Kafka.
8. **Analytics** *Обоснование:* после того, как все финансовые домены вынесены в микросевисы, новая логика Analytics сможет перехватывать все необходимые для работы данные из Kafka.
9. **Booking** *Обоснование:* самый зависимый сервис выносим в последнюю очередь.

### Общий план миграции данных одного микросервиса ###

1. Создать БД данных нового сервиса.
2. С помощью ETL перенести из монолита накопленные данные "по вчерашнее число".
3. С помощью логической репликации наладить постоянную синхронизацию данных из монолита **для данных, созданных или изменённых в монолите**.
4. При наличии на стороне монолита потребности в данных новой службы, добавить ассинхронную доставку событий из новой службы через Kafka.
5. Добавить anticorruption layer на стороне монолита, на случай прихода данных из Kafka в некорректном формате и Dead Letter Queue для сохранения очереди таких данных.
6. Запустить новую службу в режиме канареечного релиза и.
7. Провести сравнительный анализ процессов обработанных новой службой и оставшейся в монолите логикой выносимого домена.
8. Полностью переключить трафик на новую службу и отключить логическую репликацию из монолита.

### Последствия ###

**✅ Положительные:**

1. Миграция без остановки бизнеса.
2. Минимизация риска потери данных.
3. Повышение производительности системы.
4. Возможность масштабирования отдельных модулей.
5. Возможность кастомизации логики отдельных модулей в зависимости от региона.
6. Повышение независимости команд разработчиков.
7. Повышение частоты выпуска новых релизов.

**⚠️ Негативные:**

1. Усложнение инфраструктуры.
2. Потребуется больше инженеров.

**↗️ Зависимости:**

1. Появляется новая зависимость от систем контейнеризации.

### 4. Альтернативы

1. Заменить всю систему за один большой апдейт (антипаттерн *Big Bang*). *Отклонено* так есть большой риск получить неработоспособную систему и период недоступности системы в несколько часов. При тебовании к 99,95% доступности, теоретически можно себе позволить паузу в работе системы длинной в 4 часа в год, но если есть возможность избежать этого, то лучше зарезервировать это время для других экстренных ситуаций.

2. Заменить сервисы в другом порядке. Предлагаемый порядок замены на данном является предпочтительным, но при появлении новых обстоятельтств может быть изменён. Уже начатый вынос может быть отложен или откачен назад.

### 5. Риски

1. **Дублирование данных в процессе миграции.**  
   *Меры: Дублирование самоустранится после полного перехода на микросервисы*. 

2. **Отсутствие полностью консистентного состояния в распределённой системе**  
   *Меры: В виду ассинхронности взаимодействий отсутствие полностью консистентного состояния является фичей распределённых систем. Чёткие картины данных можно будет получать с запозданием в сервисе аналитики.*
