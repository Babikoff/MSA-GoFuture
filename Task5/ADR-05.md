## 1. Контекст ##

«GoFuture» стремится быстро запускать решения для партнёров в новых регионах с полной изоляцией данных и кастомизацией функциональности. Поэтому разработайте дизайн мультитенантной платформы, который будет включать модель изоляции данных между партнёрами, IAM-систему с ролевым доступом и SSO, автоматизированный процесс подключения новых партнёров (onboarding) и систему мониторинга мультитенантного окружения.

## 3. Решение ##

Для решение данной задачи предлагается реализовать сервис с несколькими уровнями стоимости (и соответственно изоляции данных и производительности): 

| Уровень | Способ изоляции | Описание |
|---|---|---|
| **Enterprise** | Отдельный сервер БД, отдельный сервер брокера сообщений | Полная изоляция, возможность автомасштабирования |
| **Standard** | Общий сервер БД с отдельной схемой БД, общий сервер брокера сообщений с отдельными топиками | Частичная изоляция данных |
| **Starter и Trial** | Общий сервер БД, общая БД, разделение данных в таблицах по TenantId.<br>Общий сервер брокера сообщений, общие топики, разделение данных по партициям | Минимальная изоляция данных |

### Роли и доступ к данным ###

#### Роли глобального уровня ####

1. **Глобальный админ** - поддерживает функциональность всей системы в целом на уровне "над тенантами". Имеет доступ ко всем данным.

2. **Техподдержка** - имеет возможность читать все данные для расследования инцидентов.

#### Роли уровня тенанта ####

1. **Админ тенанта** - управляет данными тенанта. Имеет права на создание и изменение пользователей тенанта, управляет RBAC внутри тенанта.
2. **Менеджер** - управляет данными по водителям, автомобилям и пр.
3. **Водитель** - принимает заказы, читает свои данные, запрашивает оплату.
4. **Пассажир** - делает заказы, читает и измененяет свои личные данные, делает оплату.

#### Онбоардинг партнёра ####

1. Создаётся запись в БД всех тенантов, создаётся пароль админа тенанта, генерируется *tenantId*.

2. Через Keycloak Admin API создаётся новый Realm для тенанта с пользователем "админ".

3. В зависимости от выбранного тарифа создаются либо новые сервисы в Kubernetes (для Enterprise), либо добавляются схемы и топики в общий сервер БД и брокер Kafka (для Standard). Для Started и Trial добавляются только новые партиции в Kafka.

4. По мере добавления админом новых пользователей (водителей и прочих сотрудников) их данные автоматически синхронизируются в Keycloak.

#### Создание trial тенанта ####

В целях безопасности и экономии, trial тенанты создаются отдельно от общих клиентов и используют режим максимального разделения данных

1. Создаётся запись в БД всех тенантов, создаётся пароль админа тенанта, генерируется *tenantId*.

2. Через Keycloak Admin API создаётся новый Realm для тенанта с пользователем "админ".

3. Добавляются новые партиции в сервере Kafka для триалов. Используется отдельный сервер БД.

4. По мере добавления админом новых пользователей (водителей и прочих сотрудников) их данные автоматически синхронизируются в Keycloak.


### Система мультитенантного мониторинга (Prometheus + Grafana) ###

Для обеспечения прозрачности инфраструктуры при сохранении строгой изоляции данных мониторинга между арендаторами реализуется архитектура с принудительной фильтрацией по `tenant_id`.

#### 1. Модель сбора и разметки метрик (Prometheus + Exporters)
- **PostgreSQL (схемы и таблицы):**
  * Сбор осуществляется через `postgres_exporter`.
  * **Тариф Standard (разделение по схемам):** стандартные метрики (`pg_stat_user_tables`) содержат лейбл `schemaname`. Схемы именуются в формате `tenant_<tenant_id>`, из которого Prometheus с помощью `metric_relabel_configs` извлекает метку `tenant_id`.
  * **Тариф Starter / Trial (общие таблицы с колонкой tenantId):** через механизм `custom-queries.yaml` в `postgres_exporter` настраивается периодический сбор статистики (объем строк, интенсивность операций) с группировкой по `tenant_id` и отдачей лейбла `tenant_id`.
- **Kafka (топики и партиции):**
  * Сбор осуществляется через `kafka_exporter`.
  * **Тариф Standard (выделенные топики):** топики именуются с префиксом тенанта `t_<tenant_id>_<topic_name>`. Prometheus извлекает лейбл `tenant_id` через relabeling.
  * **Тариф Starter / Trial (общие топики, разделение по партициям):** метрики топиков содержат лейблы `topic` и `partition`. Привязка конкретных партиций к `tenant_id` сопоставляется через `relabel_configs` (lookup-таблицы) или микросервисные метрики приложения.

#### 2. Безопасность и изоляция на уровне запросов (prom-label-proxy)
- Для исключения утечки чужих метрик при ручном изменении PromQL-запросов перед Prometheus устанавливается легковесный open-source компонент **`prom-label-proxy`**.
- Он перехватывает все входящие HTTP-запросы и принудительно внедряет условие `{tenant_id="<id>"}` во все селекторы PromQL-выражений. Пользователь технически не может запросить метрики без своего `tenant_id` или с идентификатором чужого тенанта.

#### 3. Организация доступа и визуализация в Grafana
- **Интеграция с Keycloak (SSO / OIDC):**
  * Для каждого арендатора создается выделенная организация Grafana (`Org: Tenant_<tenant_id>`).
  * При аутентификации через Keycloak пользователь распределяется в соответствующую Grafana Org на основе атрибута `tenant_id` из токена.
- **Изолированный Data Source:**
  * В организации каждого тенанта настраивается Prometheus Data Source, указывающий на `prom-label-proxy` с параметром своего тенанта (`http://prom-label-proxy:8080/api/v1?tenant_id=<tenant_id>`).
  * Для Глобального администратора настраивается прямой Data Source к Prometheus без фильтрации (в глобальной Org Main).
- **Шаблоны дашбордов:**
  * Разрабатываются унифицированные параметризованные дашборды, отображающие:
    * Загрузку и задержки БД (TPS, table size, connection count).
    * Состояние очередей сообщений (consumer lag, message in/out rate по своим топикам/партициям).
  * Дашборды тиражируются во все организации тенантов автоматически через Grafana Provisioning.

### 4. Альтернативы

#### 4.1. Альтернативные варианты реализации мультитенантности

1. **Silo-модель (Full Isolation для всех тарифов):**
   * *Суть:* Каждому тенанту вне зависимости от тарифа выделяется отдельный стек: отдельный инстанс БД (или отдельный кластер), отдельный кластер/неймспейс Kafka, отдельные поды сервисов.
   * *Плюсы:* Идеальная физическая изоляция данных, полное исключение проблемы «шумного соседа» (noisy neighbor), простота миграций и бэкапов отдельного тенанта.
   * *Минусы:* Экстремально высокая стоимость инфраструктуры, долгий и тяжелый онбординг, неэффективное использование ресурсов для мелких таксопарков (Starter/Trial), сложность централизованного сопровождения десятков/сотен инстансов.

2. **Pool-модель (Полностью единая инфраструктура с логической изоляцией):**
   * *Суть:* Все данные всех тенантов (включая Enterprise) хранятся в одной базе данных с разделением на уровне `tenant_id` в строках (Row-Level Security, RLS в PostgreSQL), а сообщения идут через общие топики Kafka с `tenant_id` в заголовке сообщения (Kafka Headers).
   * *Плюсы:* Минимальная стоимость инфраструктуры, максимально простой онбординг (создание тенанта — просто строка в БД), эффективная утилизация вычислительных ресурсов.
   * *Минусы:* Высокие риски утечки данных при ошибке в коде сервиса или политиках RLS; уязвимость к эффекту «шумного соседа»; невозможность предоставить крупным enterprise-клиентам регуляторное соответствие (например, требование физической изоляции данных); трудности шардирования и выборочного восстановления данных одного клиента.

3. **Изоляция на уровне отдельных баз данных на общем сервере СУБД (Database-per-tenant):**
   * *Суть:* Использование общего сервера СУБД (PostgreSQL), но для каждого тенанта создается отдельная база данных (а не просто схема).
   * *Плюсы:* Более строгая изоляция, чем схемы (разные каталоги метаданных, независимые права доступа на уровне БД), независимый бэкап через стандартный `pg_dump`.
   * *Минусы:* Высокий оверхед по оперативной памяти (пулы соединений `pgbouncer` не могут эффективно переиспользоваться между разными БД), ограничение на общее количество активных БД на одном хосте PostgreSQL.

#### 4.2. Альтернативные варианты системы мониторинга

1. **Специализированные мультитенантные TSDB (VictoriaMetrics / Grafana Mimir / Cortex):**
   * *Суть:* Замена Prometheus на системы, изначально спроектированные для мультитенантности (например, VictoriaMetrics Cluster или Grafana Mimir). В них изоляция реализована на уровне ядра с разделением данных по HTTP-заголовку (например, `X-Scope-OrgID`).
   * *Плюсы:* Нативная изоляция «из коробки» без внешних прокси-фильтров; раздельное физическое хранение метрик тенантов; горизонтальная масштабируемость и высокая плотность хранения.
   * *Минусы:* Существенное усложнение эксплуатационного стека (требуются компоненты распределенного кластера: ingester, distributor, querier, compactors); избыточно для текущего объема инфраструктуры.

2. **Выделенный стек мониторинга на каждого тенанта (Dedicated Prometheus per Tenant):**
   * *Суть:* Для каждого тенанта разворачивается собственный легковесный под Prometheus (или Grafana Agent), собирающий только метрики его ресурсов.
   * *Плюсы:* 100% изоляция данных метрик, отсутствие риска утечки или обхода фильтров.
   * *Минусы:* Неприменимо для общих серверов БД и очередей брокера (экспортеры `postgres_exporter` и `kafka_exporter` опрашивают весь сервер целиком); перерасход CPU/RAM на запуск сотен инстансов Prometheus.

3. **Разделение только на уровне прав Grafana Dashboard / Variables (Без проксирования):**
   * *Суть:* Прямое подключение Grafana к единому Prometheus с переменной дашборда `$tenant_id`, скрытой от изменения пользователем.
   * *Плюсы:* Минимальная архитектурная сложность, отсутствие промежуточных компонентов вроде `prom-label-proxy`.
   * *Минусы:* Нулевая безопасность изоляции данных. Любой пользователь тенанта с правами исследователя (Explore) или через DevTools браузера может отправить произвольный PromQL-запрос и прочитать метрики любых других клиентов.

### 5. Риски

1. **Риск: Проблема «шумного соседа» (Noisy Neighbor) в общих хранилищах и брокере (тарифы Standard, Starter, Trial).**  
   *Описание:* Аномально высокая активность или некорректные запросы одного тенанта могут исчерпать ресурсы общего сервера PostgreSQL (CPU, IOPS, connection pool) или вызвать деградацию партиций/топиков Kafka, замедляя работу остальных арендаторов.  
   *Меры устранения:*
   * Настройка квот и лимитов на уровне PostgreSQL: использование `pgbouncer` с лимитами подключений на пользователя/схему (`max_user_connections`), настройка `statement_timeout` для предотвращения зависших «тяжелых» запросов.
   * Настройка квот в Apache Kafka: применение механизма `Client Quotas` по `user-principal` / `client-id` для ограничения полосы пропускания (produce/fetch byte-rate квоты) и процента использования времени запросов брокера (`request_percentage`).
   * Алертинг в Prometheus по превышению пороговых квот отдельным `tenant_id` и автоматическое/ручное предложение клиенту апгрейда на тариф Enterprise.

2. **Риск: Утечка межтенантных данных или обход изоляции мониторинга через прямой доступ к Prometheus.**  
   *Описание:* Ошибки в сетевой сегментации или конфигурации Grafana могут позволить пользователю отправить PromQL-запрос в обход `prom-label-proxy`, получив доступ к метрикам всех тенантов и внутренним техническим параметрам всей инфраструктуры.  
   *Меры устранения:*
   * Сетевая изоляция (Kubernetes NetworkPolicies / Firewall): запрет любого прямого входящего трафика на порт Prometheus из внешних сетей и пространств имен приложений. Разрешить доступ к API Prometheus исключительно из пода `prom-label-proxy` и внутренней сети глобального администрирования.
   * Ролевая модель в Grafana: отключение прав администратора сервера у локальных админов тенантов (назначение роли `Viewer` или `Editor` строго внутри своей Organization), блокировка доступа к редактированию источников данных (Data Sources).
   * Регулярное автоматизированное тестирование безопасности (Security Audits & Pen-testing) на попытки инъекций в PromQL-запросы и обхода лейбл-фильтров.

3. **Риск: Деградация производительности PostgreSQL и Prometheus из-за сбора кастомных метрик по `tenant_id` (Cardinality Explosion & Slow Queries).**  
   *Описание:* На тарифах Starter/Trial таблицы являются общими. Регулярные SQL-запросы `postgres_exporter` для агрегации метрик по миллионам строк с группировкой по сотням `tenant_id` создадут паразитную нагрузку на СУБД. Кроме того, рост числа тенантов приведет к лавинообразному росту кардинальности (high cardinality) временных рядов в Prometheus.  
   *Меры устранения:*
   * Оптимизация сбора в СУБД: сбор детальной аналитики не «в лоб» через `COUNT(*)/SUM()` по «живым» OLTP-таблицам, а по служебным инкрементальным счетчикам, статистическим представлениям PostgreSQL (`pg_stat_user_tables`) либо асинхронный расчет агрегатов через легковесные триггеры/демоны с записью в отдельную таблицу метрик `tenant_usage_stats`.
   * Контроль кардинальности: для базовых инфраструктурных метрик ограничить глубину детализации, а высокочастотный биллинг/бизнес-метрики вынести в специализированный ClickHouse/ELK.
   * Увеличение интервала опроса (scrape interval) для тяжелых кастомных запросов (например, опрос раз в 1–5 минут вместо 15 секунд).
