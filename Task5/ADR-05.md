# ADR-05: Разработка дизайна мультитенантной платформы.

**Статус:** ⚠️ На рассмотрении
**Участники:** Иван Бабиков  
**Дата:** 2026-11-02  

---

## 1. Контекст

«GoFuture» стремится быстро запускать решения для партнёров в новых регионах с полной изоляцией данных и кастомизацией функциональности. Поэтому разработайте дизайн мультитенантной платформы, который будет включать модель изоляции данных между партнёрами, IAM-систему с ролевым доступом и SSO, автоматизированный процесс подключения новых партнёров (onboarding) и систему мониторинга мультитенантного окружения.

## 3. Решение

Для решение данной задачи предлагается реализовать сервис с несколькими уровнями стоимости (и соответственно изоляции данных и производительности): 

| Уровень | Способ изоляции | Описание |
|---|---|---|
| **Enterprise** | Отдельный сервер БД, отдельный сервер брокера сообщений | Полная изоляция, возможность автомасштабирования |
| **Standard** | Общий сервер БД с отдельной схемой БД, общий сервер брокера сообщений с отдельными топиками | Частичная изоляция данных |
| **Starter и Trial** | Общий сервер БД, общая БД, разделение данных в таблицах по TenantId.<br>Общий сервер брокера сообщений, общие топики, разделение данных по партициям | Минимальная изоляция данных |

### Роли и доступ к данным ###

#### Роли глобального уровня ####

1. **Глобальный админ** - поддерживает функциональность всей системы в целом на уровне "над тенантами". Имеет доступ ко всем данным.

2. **Техподдержка** - имеет возможность читать все данные для расследования инцидентов.

#### Роли уровня тенанта ####

1. **Админ тенанта** - управляет данными тенанта. Имеет права на создание и изменение пользователей тенанта, управляет RBAC внутри тенанта.
2. **Менеджер** - управляет данными по водителям, автомобилям и пр.
3. **Водитель** - принимает заказы, читает свои данные, запрашивает оплату.
4. **Пассажир** - делает заказы, читает и измененяет свои личные данные, делает оплату.

#### Онбоардинг партнёра ####

1. Создаётся запись в БД всех тенантов, создаётся пароль админа тенанта, генерируется *tenantId*.

2. Через Keycloak Admin API создаётся новый Realm для тенанта с пользователем "админ".

3. В зависимости от выбранного тарифа создаются либо новые сервисы в Kubernetes (для Enterprise), либо добавляются схемы и топики в общий сервер БД и брокер Kafka (для Standard). Для Started и Trial добавляются только новые партиции в Kafka.

4. По мере добавления админом новых пользователей (водителей и прочих сотрудников) их данные автоматически синхронизируются в Keycloak.

#### Создание trial тенанта ####

В целях безопасности и экономии, trial тенанты создаются отдельно от общих клиентов и используют режим максимального разделения данных

1. Создаётся запись в БД всех тенантов, создаётся пароль админа тенанта, генерируется *tenantId*.

2. Через Keycloak Admin API создаётся новый Realm для тенанта с пользователем "админ".

3. Добавляются новые партиции в сервере Kafka для триалов. Используется отдельный сервер БД.

4. По мере добавления админом новых пользователей (водителей и прочих сотрудников) их данные автоматически синхронизируются в Keycloak.


### Система мультитенантного мониторинга (Prometheus + Grafana) ###

Для обеспечения прозрачности инфраструктуры при сохранении строгой изоляции данных мониторинга между арендаторами реализуется архитектура с принудительной фильтрацией по `tenant_id`.

#### 1. Модель сбора и разметки метрик (Prometheus + Exporters)
- **PostgreSQL (схемы и таблицы):**
  * Сбор осуществляется через `postgres_exporter`.
  * **Тариф Standard (разделение по схемам):** стандартные метрики (`pg_stat_user_tables`) содержат лейбл `schemaname`. Схемы именуются в формате `tenant_<tenant_id>`, из которого Prometheus с помощью `metric_relabel_configs` извлекает метку `tenant_id`.
  * **Тариф Starter / Trial (общие таблицы с колонкой tenantId):** через механизм `custom-queries.yaml` в `postgres_exporter` настраивается периодический сбор статистики (объем строк, интенсивность операций) с группировкой по `tenant_id` и отдачей лейбла `tenant_id`.
- **Kafka (топики и партиции):**
  * Сбор осуществляется через `kafka_exporter`.
  * **Тариф Standard (выделенные топики):** топики именуются с префиксом тенанта `t_<tenant_id>_<topic_name>`. Prometheus извлекает лейбл `tenant_id` через relabeling.
  * **Тариф Starter / Trial (общие топики, разделение по партициям):** метрики топиков содержат лейблы `topic` и `partition`. Привязка конкретных партиций к `tenant_id` сопоставляется через `relabel_configs` (lookup-таблицы) или микросервисные метрики приложения.

#### 2. Безопасность и изоляция на уровне запросов (prom-label-proxy)
- Для исключения утечки чужих метрик при ручном изменении PromQL-запросов перед Prometheus устанавливается легковесный open-source компонент **`prom-label-proxy`**.
- Он перехватывает все входящие HTTP-запросы и принудительно внедряет условие `{tenant_id="<id>"}` во все селекторы PromQL-выражений. Пользователь технически не может запросить метрики без своего `tenant_id` или с идентификатором чужого тенанта.

#### 3. Организация доступа и визуализация в Grafana
- **Интеграция с Keycloak (SSO / OIDC):**
  * Для каждого арендатора создается выделенная организация Grafana (`Org: Tenant_<tenant_id>`).
  * При аутентификации через Keycloak пользователь распределяется в соответствующую Grafana Org на основе атрибута `tenant_id` из токена.
- **Изолированный Data Source:**
  * В организации каждого тенанта настраивается Prometheus Data Source, указывающий на `prom-label-proxy` с параметром своего тенанта (`http://prom-label-proxy:8080/api/v1?tenant_id=<tenant_id>`).
  * Для Глобального администратора настраивается прямой Data Source к Prometheus без фильтрации (в глобальной Org Main).
- **Шаблоны дашбордов:**
  * Разрабатываются унифицированные параметризованные дашборды, отображающие:
    * Загрузку и задержки БД (TPS, table size, connection count).
    * Состояние очередей сообщений (consumer lag, message in/out rate по своим топикам/партициям).
  * Дашборды тиражируются во все организации тенантов автоматически через Grafana Provisioning.
